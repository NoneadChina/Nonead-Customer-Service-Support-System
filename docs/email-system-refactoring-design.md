# 邮件发送体系重构设计文档

> **状态（2026-11-23 复核，v2.3.0 工作树）**：本文档 v1.5（2026-08-28）为设计稿，文中「三路径 / 两套模板」的收敛方案已随之落地；现行实现与配置口径以代码和 `docs/development.md` §9（邮件与本地化）为准，本文保留为重构决策记录。

## 一、背景与目标

### 1.1 现状问题

当前系统中有 **3 条独立的邮件发送路径** 和 **2 套模板体系**，架构混乱，用户难以理解和管理：

| 发送方式 | 触发方式 | 模板体系 | 典型场景 |
|---------|---------|---------|---------|
| 系统内置 | 业务代码直接调用 `EnqueueEmailAsync` | `MailTemplate` (系统模板) | 新会话通知、会话分配、会话关闭、密码重置 |
| 通知规则 | 事件驱动 `NotificationService.SendNotificationAsync` | `NotificationTemplate` | SLA 预警/违规、各类提醒 |
| 工作流自动化 | 工作流引擎 "发送邮件" 动作 | `MailTemplate` (自定义模板) | 自定义业务流程 |

核心痛点：
- 系统内置邮件硬编码，用户无法开关或修改
- 两套模板体系并存，变量不统一
- 用户不知道哪些邮件在哪里配置
- 命名无规范，无法快速识别哪些是发邮件的

### 1.2 重构目标

1. **职责清晰**：工作流自动化 和 通知规则 各归其位，边界明确
2. **可配置化**：系统内置邮件都迁移到工作流，用户可开关、可改模板、可加条件
3. **命名规范**：发邮件的条目有统一前缀，一眼可识别
4. **模板可预览**：邮件模板和通知模板都支持预览功能
5. **渐进式改造**：不做破坏性变更，分步实施

- 两套模板各归其主，互不干扰

## 三、详细设计

### 3.1 系统内置邮件迁移到工作流自动化

#### 3.1.1 迁移范围

| 邮件类型 | 当前代码位置 | 迁移后触发事件 | 是否迁移 |
|---------|-------------|---------------|---------|
| 新会话通知 | `ConversationService.NotifyNewConversationAsync` | `new_conversation` | ✅ 是 |
| 会话分配通知 | `ConversationAssignmentService.SendAssignmentNotificationAsync` | `assignee_changed` | ✅ 是 |
| 会话关闭通知 | `ConversationStatusService.SendConversationClosedNotificationAsync` | `conversation_closed` | ✅ 是 |
| 客户新回复通知 | `ConversationThreadService` 中 | `new_reply` | ✅ 是 |
| 密码重置邮件 | `AuthService.SendPasswordResetEmailAsync` | - | ❌ 否（系统安全相关） |
| 欢迎邮件 | `AuthService.SendWelcomeEmailAsync` | - | ❌ 否（系统安全相关） |

#### 3.1.2 工作流新增内置触发事件

| 触发事件 Key | 显示名称 | 触发时机 | 上下文变量 |
|-------------|---------|---------|-----------|
| `new_conversation` | 会话创建时 | 新会话创建并保存后 | `conversation`, `customer`, `mailbox` |
| `assignee_changed` | 会话分配时 | 会话分配或改派后 | `conversation`, `assigned_user`, `assigner` |
| `conversation_closed` | 会话关闭时 | 会话状态变更为已关闭后 | `conversation`, `customer`, `closed_by`, `satisfaction_url` |
| `new_reply` | 客户回复时 | 客户发来新回复后 | `conversation`, `customer`, `reply` |

#### 3.1.3 种子数据：默认系统工作流

系统初始化时自动创建以下工作流（`IsSystem = true`，不可删除但可停用/修改）：

| 工作流名称 | 触发事件 | 动作配置 | 关联模板 |
|-----------|---------|---------|---------|
| `[邮件] 新会话通知客服` | `new_conversation` | 发送邮件 → 被分配客服邮箱 | 新会话通知 |
| `[邮件] 会话分配通知` | `assignee_changed` | 发送邮件 → 被分配客服邮箱 | 会话分配通知 |
| `[邮件] 会话关闭通知客户` | `conversation_closed` | 发送邮件 → 客户邮箱 | 会话关闭通知 |
| `[邮件] 客户新回复通知` | `new_reply` | 发送邮件 → 当前处理客服邮箱 | 新回复通知 |

#### 3.1.4 改造策略

1. 业务代码中移除直接发邮件的逻辑，改为触发工作流事件
2. 如果没有匹配的工作流，不发邮件（不再硬编码兜底）
3. 种子数据确保新安装的系统有默认的工作流配置
4. 升级系统时，检测是否已有这些工作流，没有则自动创建

### 3.2 工作流"发送邮件"动作增强

#### 3.2.1 收件人选项扩展

现有"发送邮件"动作的收件人支持：
- ✅ 固定邮箱地址
- ✅ 模板变量

新增支持：
- 会话客户邮箱（`{{conversation.customer_email}}`）
- 被分配客服邮箱（`{{conversation.assigned_user.email}}`）
- 指定角色的所有成员
- 指定团队的所有成员
- 指定邮箱（Mailbox）的所有成员

#### 3.2.2 邮件模板选择器

- 动作配置中直接选择 `MailTemplate`
- 按分类筛选：全部 / 系统内置 / 工作流 / 自定义
- 选择模板后显示该模板的变量列表，以及当前工作流上下文中可提供的变量

### 3.3 命名规范

| 位置 | 命名规则 | 示例 |
|------|---------|------|
| 工作流中发邮件的条目 | 名称前缀加 `[邮件]` | `[邮件] 新会话通知客服` |
| 通知规则中发邮件的规则 | 名称前缀加 `[邮件]` | `[邮件] SLA 超时预警` |

用户在列表中一眼就能识别哪些是发邮件的配置。

### 3.4 模板预览功能

#### 3.4.1 通知模板预览

新增 API：`POST /api/notification-templates/{id}/preview`

功能：
- 用模拟数据填充模板变量，实时渲染预览
- 每个事件类型提供一套默认模拟数据
- 预览内容：邮件主题 + 邮件正文（HTML 渲染）
- 可选：发送测试邮件到指定邮箱

#### 3.4.2 邮件模板预览

新增 API：`POST /api/mail-templates/{id}/preview`

功能与通知模板预览一致，确保两套模板的编辑体验统一。

#### 3.4.3 模拟数据规范

为每个事件类型定义标准的模拟数据结构，例如：

```json
{
  "conversation": {
    "id": 123,
    "number": "CNV-20260725-001",
    "subject": "产品使用问题咨询"
  },
  "customer": {
    "name": "张三",
    "email": "zhangsan@example.com"
  }
}
```

## 五、实施步骤

### 阶段一：基础设施

1. 工作流新增 `IsSystem` 字段，支持系统内置工作流
2. 复用工作流已有的 4 个触发事件（new_conversation/assignee_changed/conversation_closed/new_reply）实现邮件迁移
3. 工作流"发送邮件"动作增强收件人选项
4. 邮件模板和通知模板增加预览功能

### 阶段二：迁移系统内置邮件

1. 新会话通知迁移到工作流
2. 会话分配通知迁移到工作流
3. 会话关闭通知迁移到工作流
4. 客户新回复通知迁移到工作流
5. 添加种子数据和升级迁移逻辑

### 阶段三：命名规范与体验优化

1. 现有系统工作流命名加 `[邮件]` 前缀
2. 通知规则中发邮件的规则命名加 `[邮件]` 前缀
3. 工作流和通知规则列表增加筛选：只看发邮件的
4. 文档和帮助说明更新

## 六、风险与注意事项

1. **向后兼容**：升级时需确保现有用户的系统内置邮件不会突然停掉，通过自动创建默认工作流来保证
2. **性能影响**：工作流引擎比直接发邮件多了一层，需要评估性能影响（预计可忽略）
3. **用户教育**：改造后需要引导用户理解新的配置方式
4. **安全边界**：密码重置、欢迎邮件等涉及安全的邮件，继续保留为系统内置，不开放给工作流

---

## 七、验收标准

1. 所有系统内置业务邮件（新会话/分配/关闭/回复）都通过工作流发送
2. 用户可以在工作流管理页面看到这些系统工作流，并可以停用/修改
3. 邮件模板和通知模板都支持预览功能
4. 发邮件的工作流和通知规则都有 `[邮件]` 前缀

## 八、v2.2.1 同步修订（2026-08-11：邮件链路日志结构化 + CRLF 深度防御）

> 本设计文档描述的"系统邮件 → 工作流化"方案保持不变；以下为 v2.2.0 → v2.2.1 在**邮件实际发送链路**上新增的修复，邮件重构落地时需一并继承。

### 8.1 日志结构化（F-C3 修复对应本节）

**三处链路必须结构化输出（conversationId / emailId / reason / exceptionStack，缺一不可）**：

| 链路位置 | 类/方法 | 级别 | 要求 |
|----------|---------|------|------|
| Job 入队 | `ConversationEmailJob.Execute(IJobExecutionContext)` | Warning | 入队失败（Quartz 调度/反序列化异常）必须带 conversationId 和 emailId |
| 分发器 | `EmailDispatcher.DispatchAsync` | Error | SMTP 连接 / 认证 / 550 拒收 等发送失败 |
| 邮件服务 | `EmailService.SendNotificationSafeAsync` / `SendSafeAsync` / `SendInternalSafeAsync` | Warning | 外层 catch 吞异常时，内部仍需记录 reason + stack，否则原 `catch { return false; }` 完全不可观测 |

### 8.2 CRLF / C0 字符深度防御

所有三处邮件发送路径统一调用 `SanitizeHeaderInput(string input)`：

```csharp
private static string SanitizeHeaderInput(string input)
{
    if (string.IsNullOrWhiteSpace(input)) return input;
    // 1) 移除所有 C0 控制字符（\0-\x1F 含 \r\n \t 之外的其他控制字符，\x7F DEL）
    var sanitized = Regex.Replace(input, @"[\x00-\x08\x0B\x0C\x0E-\x1F\x7F]", "");
    // 2) RFC 5322 折叠长度单段 ≤ 998 字符，超过裁剪
    if (sanitized.Length > 998) sanitized = sanitized.Substring(0, 998);
    return sanitized;
}
```

应用对象：
- `To / Cc / Bcc / From / Reply-To / Subject / Message-ID / In-Reply-To / References`
- 自定义邮件头 `X-*`

### 8.3 与 v2.2.1 "密码重置邮件"的衔接

- `ResetPassword` 成功后同时撤销所有 Refresh Token + 未使用重置 Token（参见 S-M3 修复）。
- 密码重置邮件（`EmailService.SendPasswordResetEmailAsync`）调用 `SanitizeHeaderInput` 清理收件人邮箱；并在邮件正文中使用 `WebUtility.HtmlEncode` 编码用户名，避免反射型 XSS。

## 九、v2.2.9 运维基线对齐（2026-08-28：邮件发送链路 DDL & SOP 补充）

### 9.1 邮件链路涉及表的 DDL 补丁覆盖（与 §4 数据库变更联动）

| 表 | 说明 | v2.2.9 是否已纳入 9 表通用补丁 | 热修复 SQL（漂移时） |
|---|---|---|---|
| `EmailQueues` | 邮件发送主队列表 | ✅ RowVersion 覆盖 | `ALTER TABLE EmailQueues ADD COLUMN RowVersion BLOB NULL;` |
| `MailTemplates` | 系统内置 / 工作流自定义邮件模板 | ✅ 覆盖 | 同上（替换表名） |
| `NotificationTemplates` | 通知规则模板 | ✅ 覆盖 | 同上 |
| `SendLogs` | 发送记录（§8.2 CRLF 防御落地数据） | ✅ 覆盖 | 同上 |
| `Attachments` | 邮件附件 | ✅ 覆盖 | 同上 |

### 9.2 邮件主题硬编码会话 ID（§7 验收标准补充 2 条）

- **§7 新增第 9 条**：通过 IMAP 收取的客户回复触发的邮件自动回传，主题必须包含 `[#会话ID]` 占位符并使用 `conversation.Number` 实际值回填（会话回复匹配兜底必需），同时设置 `In-Reply-To`、`References` 头为对应的原始 Message-Id；生成的 Message-Id 必须写回 `Threads`（或对应主表）供后续回复串关联。
- **§7 新增第 10 条**：通过工作流 / 通知规则 / 系统内置三种路径发送的邮件，主题 `[#会话ID]` 格式必须与 9 保持一致，否则 IMAP 收取无法匹配到既有会话 → 会错误触发 `new_conversation` 规则；工作流失败不得阻塞主邮件发送，所有 workflow 异常必须 try-catch 并写入日志。

### 9.3 风险项补充（对应 §6 风险与注意事项）

| 风险 | 概率 | 影响 | v2.2.9 缓解措施 |

| 邮件工作流动作触发时，因 schema 漂移抛 SQLite Error 1，阻塞 IMAP 收取主流程 | 中 | 高 | IMAP 收取 path 的工作流执行（new_conversation / new_reply）全部 try-catch 隔离，失败仅记日志，不阻止邮件入库 |
